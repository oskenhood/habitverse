## 4. Критическая доменная логика (не сломать!)

### Расписание (`dueOn` / `is_due_on`)
5 типов: `daily` · `weekdays` (`freq_days`: **0 = Пн … 6 = Вс**) · `interval` (каждые N дней от `start_date`)
· `weekly` (`freq_days[0]`) · `monthly` (`freq_days` = числа 1…31).
Плюс границы: `key < start_date` → false; `end_date` && `key > end_date` → false; `archived` → false.

⚠️ **Нумерация дней: 0 = понедельник** (не воскресенье!). И в TS, и в SQL (`extract(isodow) - 1`).

### Стрик — семантика, которую нельзя менять молча
1. Считается **только по плановым дням**, не по календарным.
2. **Сегодняшний день не обнуляет стрик**: если сегодня плановый день ещё не закрыт,
   счётчик показывает стрик по вчерашний день включительно. После отметки вырастает на 1.
   *(Это был баг v1.0 — утром пользователи видели «0». Не откатывать!)*
   ⚠️ В демо v1.2/v2 из-за off-by-one отметка сегодняшнего дня увеличивала стрик на **2** (баг B-1,
   закреплённый старыми тестами как «эталон»). В web-движке (`web/src/lib/engine.ts`) исправлено:
   ровно +1. Демо заморожено — там старое поведение. См. граблю №51.
3. `done` и `skip` продолжают стрик **и инкрементируют счётчик** (`skip` = осознанный отдых, даёт меньше XP).
   **Замороженный `miss` продолжает стрик, но счётчик НЕ инкрементирует** — см. граблю №32.
4. `miss` рвёт стрик, **если** в его календарном месяце не осталось заморозок.
5. День **без записи** (`null`) стрик рвёт и заморозкой **не** спасается.
   Иначе старая незаполненная история сжигала весь бюджет за один проход.
6. Потраченная заморозка пишется в сам лог: `{ status:'miss', d:<дата>, frozen:true }`.
   **Благодаря этому расчёт детерминирован** и не зависит от порядка вызовов `streakOf`.
7. Бюджет заморозок **помесячный**: 2 заморозки = 2 в сентябре + 2 в октябре.
8. Заморозка за прошлый месяц НЕ списывается из текущего бюджета.
9. `best` (рекорд) считается по тем же правилам, но **сегодняшние дни в него не входят**.

### Финансы (F-2) — семантика расчётов, которую нельзя менять молча
Закреплена секцией 12 `tests/engine.web.test.js` (15 проверок). При переносе в SQL (5.4) — сверять.
1. **Периоды:** `finPeriod('week')` — понедельник…воскресенье (0 = Пн, как во всём движке);
   `month` — 1-е…последнее число (високосный февраль учтён); `days` — число дней в диапазоне.
2. **`avgPerDay` = total / days диапазона** (не «дней с тратами») — предсказуемо для прошлых периодов.
3. **Тип расхода хранится строкой в нижнем регистре** (trim, ≤40, пустой → «прочее»);
   агрегации — по этой строке; отображение — `capFirst` + `expenseTypeStyle` (пресет → свои
   иконка/цвет, пользовательский → coin + мягкий тон по стабильному хешу).
4. **`topNames`** — агрегат одинаковых имён (ключ — trim+lowercase, отображение — первое встреченное
   написание), сортировка по total desc, `best` — крупнейшая запись агрегата.
5. **Пьедестал (`podium`)** — топ-3 ОТДЕЛЬНЫХ записей по сумме (не агрегатов), тай-брейк — свежие
   выше (ts desc). Это осознанно: «первое место по тратам и цитата пользователя» — одна запись.
6. **`fmtMoney`:** «1 234,5 ₽» — пробел-разделитель тысяч, запятая-десятичка, trailing-нули копеек
   срезаются, минус — «−» (U+2212). Смоук сверяет KPI с `fmtMoney` движка — менять формат = чинить тесты.
7. **Реестр показывает ВСЕ записи** (период влияет только на сводки) — осознанное решение:
   трата «задним числом» не исчезает из вида. Сортировка строк — date desc, ts desc.
8. Валидация `add/updateExpense` **до мутации** (грабля №59): сумма > 0 и ≤ 1e12, имя непустое ≤120.
